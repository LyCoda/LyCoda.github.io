Checking two heart-rate sensors against each other

A gate-level digital system that reads heart-rate values from an ECG and a pulse oximeter, measures how far they disagree and escalates an alarm when the gap keeps exceeding a threshold.

My roleDesigned and built the full system for a four-person team
ContextCity, University of London · EE2600 Digital Design · Group B5

At a glance

I designed and built the whole circuit for our group, from the input shift registers to the alarm logic, and tested each block against expected outputs. Every block was assembled from flip-flops and logic gates rather than ready-made library parts.

Two sensors, one question

An ECG measures the heart's electrical activity directly. A pulse oximeter estimates heart rate indirectly, from changes in light absorption as blood pulses through tissue. When both are attached to a patient, they should agree. A persistent disagreement suggests one of them is failing.

The brief was a digital system that compares the two readings and raises an alert only when the difference stays beyond a tolerance, rather than on a single noisy reading. It was designed and tested in Logisim simulation with chosen test inputs, not connected to physical sensors.

How the system is organised

The design follows the signal from serial input to alarm. A central redundancy monitor sits in the middle and does the comparison.

  1. ReceiveEach sensor's 8-bit value shifts in serially through eight D flip-flops on a shared clock.
  2. CountA three-flip-flop JK counter waits for all eight bits before enabling the comparison.
  3. SubtractA gate-level two's-complement adder-subtractor computes the difference between the readings.
  4. CompareAn 8-bit comparator checks the difference against the error threshold.
  5. StoreA parallel register captures the difference whenever it reaches the threshold.
  6. AlertA counter steps the LEDs from green to amber to red as exceedances repeat.

Design choices

Most decisions traded generality for fewer control signals and blocks that could be verified one at a time.

Key design decisions and the reasoning behind them
BlockChoiceReason
Shift registersD flip-flopsOne data input and only a reset to manage; a natural fit for serial-to-parallel conversion
CounterJK flip-flops in toggle modeThree flip-flops give the eight states needed, with few extra gates
SubtractorTwo's complement with XOR gates as controlled invertersReuses full-adder hardware for subtraction
Negative resultsComparator and multiplexer swap the inputsThe larger reading is always the one subtracted from, so the difference is never negative
Comparator2-bit stages built into 4-bit and 8-bit comparatorsMost-significant bits take priority, and each level can be checked separately

Testing each block

Each block was probed in simulation against expected outputs before the system was assembled.

Block-level tests reported in the group report
BlockTestResult
Shift registerEight clock cycles of serial inputOutput shifted one bit per cycle exactly as expected
Subtractor11111111 − 00000000, and the reverse orderBoth gave 11111111, so no negative values
ComparatorGreater, less and equal casesAll three identified correctly
AlarmFour successive threshold exceedancesGreen, then amber, then red, staying red

All the tests passed, but they were functional checks with a handful of chosen inputs rather than exhaustive verification.

What I would add now

The tests show that each block works, but not where it might fail. I would now add boundary cases such as readings exactly at the threshold, timing diagrams showing when the enable signal fires, and a clear link from each requirement to the test that checks it.

I would also state the tolerance in beats per minute and explain where it came from. That clinical framing, which turns a logic exercise into a safety check, is what I later worked on directly in the regulatory and validation projects.
